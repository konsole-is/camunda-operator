- **2026-08-15 — ES suspension is delete-and-retain, not scale-to-zero (user, #37):** ECK removes the PVC of every node it scales away under either volume claim delete policy, so scaling node sets to zero would erase the data that `spec.suspend` promises to keep. The ECK wrapper now follows the pattern of the reference operator: the rendered CR always carries `volumeClaimDeletePolicy: DeleteOnScaledownOnly`; `DeleteOnSuspend` is true; the suspension status handler reports Suspended only when the applied CR has that policy, ECK observed the current generation, and no data migration runs; ocf then deletes the CR and reports Suspended while it is absent; resume recreates it and ECK reattaches the volumes by name. Consequence for deletion of an ElasticsearchCluster: the data PVCs stay (data removal is deliberate). Docs, API comment, goldens, and specs updated. **Batch D (CamundaCluster suspend):** reuse this; never scale ES to zero.
- **2026-08-15 — `status.storageSize` on ElasticsearchCluster (user, #37):** the smallest capacity that the data PVCs report (ECK label `elasticsearch.k8s.elastic.co/cluster-name`, claim name prefix `elasticsearch-data-`), falling back to the applied ECK claim size until a claim reports one. A PVC watch mapped through that label refreshes it. Rationale: a future auto-resize (PVCAutoResize) grows PVCs directly, not through spec, and consumers and the resizer itself need the observed size. **PVCAutoResize batch:** read this field, do not derive size from spec or the ECK template.
- **2026-08-15 — storageSize shrink is ignored, not refused (user, #37):** a preset baseline lowered under running clusters, or an inline value set below a previously preset-provided size, no longer halts reconciliation with `Ready=False/InvalidReference`. The controller keeps the applied data volume size, records a Warning event `StorageShrinkIgnored`, and continues. Lowering a preset for future clusters is therefore safe for existing ones. Docs for the cluster and preset updated. `make manifests` regenerated nothing: the CEL rule on the inline field is unchanged.
- **2026-08-15 — no separate `Suspended` condition (user, #37):** with `Ready` mirroring the ocf aggregate, a suspended cluster already reports `ElasticsearchReady=True/Suspended` and `Ready=True/Suspended`, and `ElasticsearchReady` carries `PendingSuspension`/`Suspending` on the way. The `Suspended` condition, `ConditionSuspended`, `ReasonSuspended`, and `SuspendedCondition` are removed; TEMPLATE.md now says a suspendable CRD reports suspension on `Ready`, never as a separate condition. **Batch D:** drop the planned `ClusterSuspended`/`ClusterNotSuspended` on CamundaCluster for the same reason.
