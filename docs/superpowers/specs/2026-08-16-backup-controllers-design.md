# Backup: LogicalBackupElasticsearch, LogicalBackupRDBMS, BackupSchedule (Batch D, first epic)

**Status:** approved in dialogue (2026-08-16), spec pending review
**Date:** 2026-08-16
**Scope:** `LogicalBackupElasticsearch` and `LogicalBackupRDBMS` (new, replace `Backup`), `BackupSchedule`
(with retention), removal of `BackupRetention`, `ObjectStorageConfig` (S3-compatible fields),
`ElasticsearchCluster` (keystore passthrough, narrowed user role), `CamundaCluster` and
`CamundaClusterPreset` (`spec.backup`, backup wiring), MinIO in the kind e2e suite

## Summary

Implement the first Batch D epic from the
[implementation order](../../crds/index.md#implementation-order): the backup CRDs. A backup
captures a restorable copy of one `CamundaCluster`. `BackupSchedule` creates backups on a cron
schedule and prunes the old ones. `LogicalRestore` and `PointInTimeRestore` consume backups in a
later epic.

The epic changes the CRD set that the docs describe today. It splits `Backup` into
`LogicalBackupElasticsearch` and `LogicalBackupRDBMS`, and it removes `BackupRetention`. The reasons
are in "Design decisions". The CRD docs are the starting point, not the contract. Where this spec
finds a better shape, the doc changes in the same PR (see "Doc deviations").

The epic is built the Batch B and C way: ocf components for Kubernetes resources, pure packages
outside ocf for external protocols (the `pkg/pgbootstrap` pattern), `conditions.Aggregate` for
`Ready`, `pkg/labels`, envtest through `internal/testenv`, and the kind e2e suite.

## What Camunda 8.9 does, and what this operator does

The design rests on facts from the Camunda 8.9 documentation. They are repeated here because the
two storage paths differ in who does the work.

**Elasticsearch path.** A backup is one coordinated set under one user-supplied backup ID. The
orchestration cluster serves two backup endpoints on the management port (9600):
`/actuator/backupHistory` for the web-application indices, and `/actuator/backupRuntime` for the
Zeebe partitions. A complete backup also needs the exported Zeebe record indices, which the
operator snapshots itself through the Elasticsearch snapshot API. Exporting is soft-paused
during the backup and resumed after it. Continuous backups are not supported on this path. The
components read the snapshot repository name from `camunda.data.backup.repository-name`.

**RDBMS path.** Backups involve two independent systems. Zeebe backs up its primary storage
itself: `camunda.data.primary-storage.backup` with `continuous`, `schedule`,
`checkpoint-interval`, and `retention`. Backup IDs are generated by the cluster. Camunda does
not back up the database. The docs assign that to the database administrator with vendor tools
such as `pg_dump`, and require the entire Camunda database including the `EXPORTER_POSITION`
table. At restore, Zeebe reads the exporter position from the restored database and selects the
matching primary-storage backups. The docs recommend a primary-storage backup after the
secondary-storage backup when the two are coordinated.

Optimize always stores its data in Elasticsearch or OpenSearch and is backed up on its own.
`CamundaOptimize` has no controller yet, so this epic does not drive Optimize (see "Deferred").

## Goals

- `LogicalBackupElasticsearch`: run the coordinated Elasticsearch procedure from the operator process,
  crash-safe, and never leave a cluster soft-paused.
- `LogicalBackupRDBMS`: dump the logical database to the backup bucket with a Job, then request one
  primary-storage backup so the CR is a complete restore point.
- `BackupSchedule`: create the backup kind that matches the storage type of the cluster on a
  cron schedule, skip overlaps and suspended clusters, and prune to
  `spec.retained.completed` and `spec.retained.failed`.
- Both backup kinds delete their own artifacts through a finalizer, keyed strictly on their
  backup ID.
- `CamundaCluster` renders the backup wiring: the Zeebe backup store on both paths, the snapshot
  repository and its registration on the Elasticsearch path, and continuous primary-storage
  backup on the RDBMS path. `CamundaClusterPreset` carries the same `spec.backup` block.
- `ObjectStorageConfig` describes S3-compatible storage (endpoint, region, path style, static
  credentials) in addition to the three cloud providers, so MinIO works in production and in
  kind.
- `ElasticsearchCluster` accepts keystore secure settings and drops the `superuser` role.
- e2e in kind proves both paths against MinIO.

## Non-goals

- Restore. `LogicalRestore` and `PointInTimeRestore` are the next epic. This epic proves that
  the artifacts exist, not that they restore.
- Optimize backup (no `CamundaOptimize` controller yet).
- Cloud infrastructure (buckets, IAM). `camunda-cloud-operator` owns that.
- Backup of the management plane (`CamundaManagementCluster`).
- A `/v2/backups` REST client (Camunda 8.10 only).
- Migration or compatibility for the scaffold `Backup` and `BackupRetention` kinds. The project
  has no releases, so the kinds are removed without a deprecation path.

## Design decisions

### Two backup kinds, not one

The Elasticsearch procedure is several independent snapshot operations under one backup ID. Its
status is a per-part map (history, records, runtime), and its restore constraints are Zeebe
shaped: partition count and cluster generation. The RDBMS procedure is one dump and one Job. Its
restore aligns through the exporter position inside the dump. Its backup ID does not identify a
Zeebe backup at all. A shared `Backup` kind would leave most of its status empty on one path and
force `LogicalRestore` to branch on which flavor it received. The production `camunda-operator`
arrived at a per-part status for exactly the Elasticsearch reason. The repository already splits
along this line, because `PointInTimeRestore` is RDBMS-only.

The counterweight is `SecondaryStorageConfig`, which models the same fork with a `type`
discriminator and two blocks. That CR is a static contract with no behavior. A discriminator
organizes fields, but it cannot separate two lifecycles, two status vocabularies, two finalizers,
and two restore contracts. The kinds are `LogicalBackupElasticsearch` and `LogicalBackupRDBMS`,
after `SecondaryStorageTypeElasticsearch` and `SecondaryStorageTypeRDBMS`.

The `LogicalBackup` prefix names the pairing with the restore kinds. A logical backup is a
discrete restore point that a user creates and deletes, and `LogicalRestore` consumes it.
`PointInTimeRestore` rides on the continuous primary-storage range that Zeebe manages, and it has
no backup CR at all. The variant is a suffix on the base concept, as in `CamundaClusterPreset`.
Only logical backups are scheduled by this operator, so `BackupSchedule` keeps its short name.
The plurals are set explicitly (`logicalbackupelasticsearches` is not typed by anyone) with the
short names `lbes` and `lbrdbms`.

### Retention lives on the schedule

`BackupRetention` was a per-cluster pruner, decoupled from any schedule so that it could prune
manual backups too. That decoupling is the reason to remove it. A pruning policy that a human
created months ago must not delete a manual pre-upgrade backup. Retention becomes
schedule-owned: a schedule prunes only the backups it created, matched by the
`camunda.io/backup-schedule` label. A deliberate backup gets a deliberate delete. This is the
CronJob shape (`successfulJobsHistoryLimit`, `failedJobsHistoryLimit`), it removes one CRD, and
it removes the admission rule that rejected two retentions for one cluster.

The old design kept failed backups forever. Under a nightly cron that starts to fail, that is a
slow leak. `spec.retained.failed` bounds it.

### The Elasticsearch procedure runs in the operator

Step 6 of the procedure, resume exporting, must always run, including after a failure in an
earlier step. A cluster left soft-paused cannot compact its log and fills its disks. A controller
re-enters after a crash, an operator restart, or a node eviction, and always resumes a cluster
that it finds soft-paused. A Job that dies between pause and resume leaves the cluster paused
until a controller notices, which rebuilds the controller machinery anyway. The RDBMS dump is a
Job regardless: gigabytes of dump do not stream through the operator process.

### Static credentials only behind an explicit endpoint

`ObjectStorageConfig` states that access is granted through workload identity and that the
contract references no Secrets. That stance survives for every cloud provider. Static keys exist
only when `endpoint` is set, which marks S3-compatible storage (MinIO, Ceph, NetApp). This is a
production capability, not a test affordance, and it lets the kind suite run the same code path
as production.

Elasticsearch reads S3 credentials from the node keystore only, never from the repository
settings. ECK fills the keystore from `spec.secureSettings`. `ElasticsearchCluster` gains the
same field as a passthrough. The keystore belongs to the ECK object that the
`ElasticsearchCluster` controller owns, so the `CamundaCluster` controller does not write it. This
matches the existing stance that the Elasticsearch nodes get their bucket access on the
`ElasticsearchCluster` (`serviceAccount.annotations` for workload identity, `secureSettings` for
static keys).

### Backup policy on the cluster and in the preset, the bucket on the cluster only

`CamundaCluster.spec.backup` holds how backups behave: the primary-storage schedule and
retention, and the placement, resources, and scratch volume of the dump Job. `backupStorageRef`
holds where they go. `CamundaClusterPresetSpec.Cluster` reuses `CamundaClusterSpec`, so
`spec.backup` is in the preset by construction. `backupStorageRef` stays in the instance-bound
exclusion list. `spec.backup` does not join it. A scheduled backup inherits the dump settings from
the cluster, so `BackupSchedule` needs no passthrough. A one-off `LogicalBackupRDBMS` can override
them.

### The RDBMS finalizer deletes the dump only

Primary-storage backups belong to the continuous range that Zeebe manages under
`retention.window`. Every restore point in the window shares them, and `PointInTimeRestore` will
use them. Deleting one because a `LogicalBackupRDBMS` CR was pruned tears a hole in that range. The
finalizer removes the dump object and nothing else.

## API

### ObjectStorageConfig

New optional fields. `accountId` becomes optional.

```yaml
spec:
  provider: aws                  # unchanged: aws | gcp | azure
  type: S3                       # unchanged: must match provider
  bucketId: arn:aws:s3:::camunda-backups
  bucketName: camunda-backups
  basePath: clusters             # unchanged
  accountId: arn:aws:iam::123456789012:role/camunda   # now optional
  region: eu-west-1              # new. Required for S3 unless endpoint is set.
  endpoint: http://minio.minio.svc:9000   # new. Marks S3-compatible storage.
  forcePathStyle: true           # new. Path-style addressing.
  credentialsSecretRef:          # new. Static keys, S3-compatible only.
    name: minio-credentials
    namespace: camunda
    accessKeyIdKey: accessKeyId
    secretAccessKeyKey: secretAccessKey
```

CEL rules:

- `credentialsSecretRef` requires `endpoint`.
- `endpoint` and `forcePathStyle` require `type: S3`.
- Exactly one of `accountId` and `credentialsSecretRef` is set.
- `type: S3` without `endpoint` requires `region`.

MinIO is modeled as `provider: aws, type: S3, endpoint: ...`. The provider enum does not widen.
The doc names this shape "S3-compatible" and explains it.

The validation controller (Batch A) gains `Ready: MissingSecret` when `credentialsSecretRef`
names a Secret or key that does not exist.

### ElasticsearchCluster

```yaml
spec:
  secureSettings:                # new, optional. Mirrors ECK SecretSource.
    - secretName: minio-es-credentials
      entries:                   # optional key remap
        - key: accessKeyId
          path: s3.client.default.access_key
        - key: secretAccessKey
          path: s3.client.default.secret_key
```

The wrapper maps the field onto `esv1.ElasticsearchSpec.SecureSettings`. The `camunda` user drops
from `superuser` to an explicit role. The exact privilege set is determined against a real ECK
cluster during implementation. The commitment of this spec is that `superuser` goes away.

### CamundaCluster and CamundaClusterPreset

```yaml
spec:
  backupStorageRef: my-backup-config      # unchanged, instance-bound
  backup:                                 # new, allowed in a preset
    primaryStorage:                       # Zeebe's own backups
      continuous: true                    # *bool. rdbms only. Default true on rdbms.
      schedule: PT1H                      # default PT1H
      checkpointInterval: PT15M           # default PT15M
      retention:
        window: P7D                       # default P7D
        cleanupSchedule: PT1H             # default PT1H
    dump:                                 # the pg_dump Job, rdbms only
      resources: {}
      extraEnv: []
      extraEnvFrom: []
      podLabels: {}
      podAnnotations: {}
      scheduling: {}                      # SchedulingSpec, whole-block replace
      scratchVolume:
        sizeLimit: 50Gi                   # emptyDir when unset
        storageClassName: fast            # PVC when set
```

Defaults follow the configuration that the Camunda docs recommend. They apply when the cluster
is RDBMS-backed and `backupStorageRef` is set. `continuous` is a pointer so that a preset can
enable it fleet-wide and one cluster can still turn it off. The block has no effect on an
Elasticsearch-backed cluster: continuous and scheduled primary-storage backups are RDBMS
capabilities, and the dump Job exists only there. CEL cannot reject the block by storage type,
because the type lives behind `storageRef`. The doc says so.

Preset merge rules for `backup`: `primaryStorage` merges per field, the cluster wins when set.
`dump.resources` uses `mergeResources`. `dump.extraEnv` uses `mergeEnv`. `dump.extraEnvFrom`
concatenates. `dump.podLabels` and `dump.podAnnotations` use `mergeMap`. `dump.scheduling`
replaces as a whole block. `dump.scratchVolume` replaces as a whole block.

### LogicalBackupElasticsearch

```yaml
apiVersion: core.camunda.io/v1
kind: LogicalBackupElasticsearch
metadata:
  name: my-cluster-1748937221
  namespace: my-cluster-ns
  labels:
    camunda.io/cluster: my-cluster
    camunda.io/backup-schedule: my-cluster-schedule   # set by a schedule
spec:
  clusterRef:                    # immutable
    name: my-cluster
    namespace: my-cluster-ns     # optional, defaults to this namespace
status:
  phase: Running                 # Pending | Running | Completed | Failed
  step: BackupRuntime            # resume marker, see state machine
  backupId: 1748937221
  partitionsCount: 3             # restore constraint
  history:  {state: Completed}
  records:  {state: Completed}
  runtime:  {state: InProgress}
  completionTime: null
  observedGeneration: 1
  conditions: [...]
```

`ClusterRef{name, namespace}` is a new shared type in `common_types.go`.

### LogicalBackupRDBMS

```yaml
apiVersion: core.camunda.io/v1
kind: LogicalBackupRDBMS
metadata: {...}                  # same labels as above
spec:
  clusterRef: {...}              # immutable
  dump:                          # optional whole-block override of the cluster's spec.backup.dump
    resources: {}
    scheduling: {}
    podAnnotations: {}
    scratchVolume: {}
status:
  phase: Running
  step: PrimaryBackup            # Dumping | PrimaryBackup
  backupId: 1748937221           # identifies the dump object
  jobName: my-cluster-1748937221-dump
  objectKey: clusters/my-cluster-ns/my-cluster-1748937221/camunda.dump
  primaryBackupId: 42            # generated by the cluster
  completionTime: null
  observedGeneration: 1
  conditions: [...]
```

`spec.dump` replaces the cluster block as a whole. It does not merge.

### BackupSchedule

```yaml
spec:
  clusterRef: {name: my-cluster}
  schedule: "0 2 * * *"          # five-field cron, UTC
  retained:                      # optional
    completed: 7                 # default 7, minimum 1
    failed: 3                    # default 3, minimum 0
status:
  lastScheduleTime: ...
  lastBackupName: my-cluster-schedule-1748937221
  observedGeneration: 1
  conditions: [...]
```

There is no "never prune" sentinel. If a compliance case needs one, `retained.completed: null`
meaning unlimited can be added later without a breaking change.

### Conditions and reasons

Shared from `conditions.go`: `Ready`, `Healthy`, `InvalidReference`, `MissingSecret`,
`ConnectionFailed`.

Declared next to the backup types, reported by both backup kinds:

| Reason | Meaning |
| --- | --- |
| `Progressing` | The backup runs. |
| `Completed` | The backup finished. |
| `Failed` | The backup failed. The message names the step. |
| `ClusterSuspended` | The cluster is suspended. Its management API is unreachable. |
| `BackupInProgress` | Another backup of this cluster is not terminal. This one waits. |
| `StorageTypeMismatch` | The kind does not match the storage type of the cluster. |
| `MissingCredentials` | The bucket has no `credentialsSecretRef` and the cluster has no `serviceAccount`. |
| `ResumeFailed` | Elasticsearch only. Resume exporting did not succeed before the deadline. |

`BackupSchedule` reports `Healthy` and `InvalidReference`. Skipped triggers are events, not
conditions.

### Layout


Deleted: `api/v1/backup_types.go`, `api/v1/backupretention_types.go`, both scaffold controllers
and tests, both CRD bases, six RBAC roles, two samples, two `PROJECT` entries, `cmd/main.go`
wiring, `docs/crds/backup.md`, `docs/crds/backupretention.md`.

### Shared skeleton (`pkg/logicalbackup`)

Both kinds are one-shot. `spec` is immutable through a CEL transition rule. Phases are `Pending`,
`Running`, `Completed`, `Failed`. Terminal phases are never re-entered. A retry is a new CR.

Pre-checks, in order, mirror `camundacluster/precheck.go`:

1. Resolve `clusterRef`. Missing cluster: `InvalidReference`.
2. Cluster has no `backupStorageRef`: `InvalidReference`.
3. Cluster is suspended: `ClusterSuspended`. Requeue.
4. Resolve `storageRef`. Storage type does not match the kind: `StorageTypeMismatch`.
5. Another backup of either kind for this cluster is not terminal: `BackupInProgress`. Stay in
   `Pending`. Requeue.

Backup ID: the Unix timestamp at which the backup left `Pending`, recorded once in
`status.backupId`. Object key layout in the bucket:
`<basePath>/<cluster-namespace>/<cluster-name>/<backupId>/...`.

Neither kind carries an owner reference to the cluster. Backups outlive the cluster.

Finalizer `core.camunda.io/backup-artifacts` on both kinds. Deletion keys strictly on the own
`backupId`. Never a repository-wide or prefix-wide delete. Best effort: if the cluster or the
bucket config is gone, record an event and release the finalizer.

### LogicalBackupElasticsearch state machine

`status.step` is the resume marker. Every step is written as: query the current state, act only
if not already started, poll. A crash mid-step re-enters and does not repeat a POST.

| Step | Action | Client |
| --- | --- | --- |
| `PauseExporting` | `POST /actuator/exporting/pause?soft=true` | camundaadmin |
| `BackupHistory` | `POST /actuator/backupHistory {backupId}`, poll `GET .../{backupId}` | camundaadmin |
| `SnapshotRecords` | create snapshot `camunda_zeebe_records_backup_<backupId>` of the record indices, poll | esadmin |
| `BackupRuntime` | `POST /actuator/backupRuntime {backupId}`, poll `GET .../{backupId}` | camundaadmin |
| `ResumeExporting` | `POST /actuator/exporting/resume` | camundaadmin |

Failure in any step does not go to `Failed` directly. It records the message and moves
`status.step` to `ResumeExporting`. The terminal phase is written only after resume succeeds. An
operator restart at any point finds a non-terminal CR whose next action is "resume exporting".

`ResumeExporting` has a deadline (default 30 minutes, controller flag). After it, the phase is
`Failed` with reason `ResumeFailed` and a Warning event. The cluster needs a human at that
point.

Per-part status: `history`, `records`, `runtime`, each `{state, failureReason}`, with states
`Pending`, `InProgress`, `Completed`, `Failed`. `status.partitionsCount` is read from the
cluster at start.

The management API is reached through the cluster's management Service on port 9600. Whether
the 8.9 management port requires authentication, and with which credentials, is not verified
yet. The first PR verifies it against the 8.9 source and the docs MCP, and `pkg/camundaadmin`
takes the result as a client option. The Elasticsearch endpoint, CA, and `camunda` user come from
`storageRef`.

Finalizer: delete the `backupHistory` snapshots and the records snapshot in Elasticsearch, and
delete the partition backup with `DELETE /actuator/backupRuntime/{backupId}`.

### LogicalBackupRDBMS state machine

| Step | Action |
| --- | --- |
| `Dumping` | Apply the Job with SSA (field manager `camunda-operator/backup`), record `status.jobName`, track the Job. Job failure: `Failed`. |
| `PrimaryBackup` | `POST /actuator/backupRuntime` without an ID, record `status.primaryBackupId`, poll to completion. |

Extra pre-checks: `storageRef` → `SecondaryStorageConfig` → `DatabaseConfig` has no
`backupCredentialsSecretRef`: `MissingSecret`. The bucket has no `credentialsSecretRef` and the
cluster has no `serviceAccount`: `MissingCredentials`.

The Job runs one pod. An initContainer from `postgres:<major>` runs `pg_dump -Fc` of the entire
logical database into a scratch volume. The major version comes from the
`DatabaseServerConfig`. The main container is the operator image with the `upload` subcommand.
It uploads the archive with `pkg/objectstore` and exits. Job success means the upload
succeeded. The pod runs under the cluster's `<name>-camunda` ServiceAccount when
`spec.serviceAccount` is set, so workload identity applies. With `credentialsSecretRef`, the keys
are mounted as env. Scratch volume: `emptyDir` with `sizeLimit` by default, a PVC when
`storageClassName` is set. Pod placement, resources, labels, annotations, and extra env come from
the effective `dump` block. `podAnnotations` matters for meshes: an injected sidecar keeps a Job
from completing.

Finalizer: delete a still-running Job, then delete the dump object. Primary-storage backups are
not touched.

### BackupSchedule

1. Parse `spec.schedule`. Compute the next trigger from `status.lastScheduleTime`, or from the
   creation time on the first reconcile.
2. At a trigger, resolve `clusterRef`. Missing: `InvalidReference`, skip.
3. Suspended cluster: skip, event, no retry of this trigger.
4. A backup created by this schedule is not terminal: skip, event.
5. Otherwise create the kind that matches the storage type of the cluster, named
   `<schedule>-<unix-timestamp>`, labeled `camunda.io/cluster` and `camunda.io/backup-schedule`.
   No owner reference to the schedule.
6. Record `lastScheduleTime` and `lastBackupName`.
7. Prune: list the backups with this schedule's label, sort `Completed` by `completionTime`,
   delete the oldest beyond `retained.completed`. Same for `Failed` and `retained.failed`.
   `Pending` and `Running` are never counted or pruned.

The schedule watches both backup kinds through a field index on the schedule label, so a phase
change triggers pruning without a timer.

### CamundaCluster wiring

A storage-type gated part of the render, active when `backupStorageRef` is set.

**Both paths.** The Zeebe backup store: `camunda.data.primary-storage.backup.store` and the
matching `s3`, `gcs`, or `azure` block, rendered as `CAMUNDA_DATA_PRIMARYSTORAGE_BACKUP_*`
through `pkg/camundaconfig`. For S3: bucket name, base path, region, endpoint,
`force-path-style-access`, and access key and secret key from `credentialsSecretRef` (mirrored
into the cluster namespace the way the OIDC client secret is). Without static keys the AWS chain
picks up workload identity from the pod ServiceAccount. With `endpoint` set, the components also
get `AWS_REQUEST_CHECKSUM_CALCULATION=WHEN_REQUIRED` and
`AWS_RESPONSE_CHECKSUM_CALCULATION=WHEN_REQUIRED`, the documented workaround for AWS SDK 2.30+
chunked encoding on S3-compatible stores.

**Elasticsearch path.** `camunda.data.backup.repository-name` on the components. Repository name:
`<cluster-name>`. A gated ocf component registers the repository in Elasticsearch through
`pkg/esadmin`: `PUT _snapshot/<name>` with type `s3`, bucket, base path
`<basePath>/<namespace>/<name>/es`, endpoint, and path style. It converges on every reconcile
with an idempotent PUT and contributes `BackupRepositoryReady` to `Ready`. Without
`backupStorageRef` it reports `Disabled`. Elasticsearch credentials for the bucket come from the
keystore, so the CamundaCluster doc points the user at `ElasticsearchCluster.spec.secureSettings`
or `serviceAccount.annotations`. The `camunda` user role narrows to what registration and
snapshots need.

**RDBMS path.** `continuous`, `schedule`, `checkpoint-interval`, and `retention` from
`spec.backup.primaryStorage`.

### Watches and indexes

- Both backup controllers watch `CamundaCluster` (suspend flips), the bucket
  `ObjectStorageConfig`, and the referenced Secrets, through `pkg/refindex`.
- The RDBMS controller owns its Job.
- The schedule watches both backup kinds by the schedule label.
- The CamundaCluster controller already watches `ObjectStorageConfig`. It also watches the
  credentials Secret of the bucket.

### RBAC

Both backup controllers: get, list, watch, update on their kind and status, and get on
`CamundaCluster`, `SecondaryStorageConfig`, `DatabaseConfig`, `DatabaseServerConfig`,
`ObjectStorageConfig`, Secrets. The RDBMS controller: full on Jobs. The schedule controller:
create, delete, list, watch on both backup kinds. The upload subcommand needs no RBAC. Editor
and viewer roles for the three kinds replace the removed ones.

## Testing

**Unit (testify, next to the code).** `pkg/camundaadmin` and `pkg/esadmin` against `httptest`
servers: every call, the failure branches, and the already-in-progress branches that make the
steps idempotent. `pkg/objectstore` against a `fileblob` bucket. `presetmerge` gains the
`backup` block including the `*bool` three-state. `schema_test.go` for the CEL rules on
`ObjectStorageConfig` (credentials without endpoint, both identities set, neither set, S3
without region or endpoint), on the immutable `clusterRef`, and on `retained` minimums. The
rendered configuration joins the golden set with a backup variant per storage path.

**Controller (Ginkgo, envtest).** State machines against a fake management API and a fake
Elasticsearch. The cases that the design exists for: a crash mid-step re-enters and does not
re-POST. A failure in any step routes through `ResumeExporting` and only then writes `Failed`.
The resume deadline yields `ResumeFailed`. A second backup for the same cluster stays `Pending`
with `BackupInProgress`. The finalizer deletes by `backupId` and releases when the cluster is
gone. The Job outcome drives the RDBMS phase and `PrimaryBackup` follows it. The schedule
creates the kind that matches the storage type, skips on suspend and on overlap, and prunes to
`retained`. Retention is tested here, not in e2e.

**e2e (kind).** MinIO from `test/utils/minio.go` and `testdata/minio.yaml`, with a bucket and a
credentials Secret. Then the production path on both backends: an `ObjectStorageConfig` with
`endpoint` and `credentialsSecretRef`, an `ElasticsearchCluster` with `secureSettings`, a
`CamundaCluster` with `backupStorageRef`. Assertions: the snapshots exist in Elasticsearch, the
objects exist in MinIO, the dump is non-empty, `primaryBackupId` is set, and exporting runs again
afterwards, queried from the actuator, not trusted from status. A `BackupSchedule` with a
one-minute cron produces one backup and skips the overlap.

Known limit: e2e proves that the artifacts exist and the cluster reports completion. It does not
prove that a backup restores. That is the restore epic.

## Implementation breakdown

Multi-PR, feature-branch model. The bucket contract, the Elasticsearch keystore, the cluster
wiring, the two backup kinds, the schedule, and the e2e suite are separately reviewable
surfaces. The plan holds the PR list, the order, and the contracts between them.

## Risks

- **S3-compatible quirks.** Chunked encoding and checksums break some stores. Mitigation: the
  `WHEN_REQUIRED` env on the components with `endpoint`, `forcePathStyle` in the contract, and
  MinIO in e2e.
- **Elasticsearch role narrowing** can break snapshots in a way that only a real cluster shows.
  Mitigation: e2e runs the full path with the narrowed role.
- **Retention across two owners on the RDBMS path.** A schedule that keeps more dumps than
  Zeebe's `retention.window` covers keeps unrestorable dumps. Mitigation: documented pairing on
  both CRD docs, and a Warning event on the schedule when its retained count times its interval
  exceeds the window of the cluster.
- **Dump size** exceeds the scratch volume. Mitigation: `sizeLimit` and the PVC option, and a
  clear Job failure that surfaces in the `Failed` message.
- **Operator reach to port 9600.** The operator process must reach the management Service.
  Network policies can block it. Mitigation: `ConnectionFailed` with the endpoint in the message.
- **e2e resources** on the runner (ES, Camunda, Postgres, MinIO). Fallback is a split job.

## Deferred

- Optimize in the Elasticsearch set. Lands with the `CamundaOptimize` epic. The doc says so.
- OpenSearch. Out of scope until `SecondaryStorageConfig` supports it.
- `priorityClassName` and `nodeSelector` on `SchedulingSpec`. A required `nodeAffinity` term
  covers `nodeSelector`. Preemption is not covered.
- A "never prune" sentinel on `retained`.
- Warning-only validation of a `spec.backup` block on an Elasticsearch-backed cluster.

## Verified facts (Camunda 8.9 docs)

- Management endpoints: `/actuator/exporting/pause?soft=true`, `/actuator/exporting/resume`,
  `/actuator/backupHistory`, `/actuator/backupRuntime`. `backupRuntime` without an ID on the
  RDBMS path returns a generated ID.
- Backup store: `camunda.data.primary-storage.backup.store` and the `s3` block with
  `bucket-name`, `endpoint`, `region`, `access-key`, `secret-key`, `force-path-style-access`,
  `base-path`. Any S3-compatible storage is supported.
- Continuous mode: `camunda.data.primary-storage.backup.continuous`, `schedule`,
  `checkpoint-interval`, `retention.window`, `retention.cleanup-schedule`. Recommended values
  `PT1H`, `PT15M`, `P7D`, `PT1H`.
- Repository name: `camunda.data.backup.repository-name`.
- The database backup is the administrator's task with vendor tools. The entire database
  including `EXPORTER_POSITION` must be backed up.
- Chunked-encoding workaround: `AWS_REQUEST_CHECKSUM_CALCULATION=WHEN_REQUIRED` and
  `AWS_RESPONSE_CHECKSUM_CALCULATION=WHEN_REQUIRED` on all brokers.
- The Camunda document store does not support MinIO. `documentStorageRef` stays untestable in
  kind. Not in scope.
- ECK v3.5.0: `spec.secureSettings []commonv1.SecretSource{secretName, entries[]{key, path}}`.
